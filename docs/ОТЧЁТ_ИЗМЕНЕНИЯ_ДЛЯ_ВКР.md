# Отчёт о выполненных изменениях в системе семантического анализа (для научного руководителя)

Краткое описание того, что было реализовано в рамках мультиагентного подхода, построения графа знаний и оценки качества.

---

## 1. Мультиагентная архитектура

### 1.1. Базовые типы (`semantics_analysis/multi_agent/base.py`)

- **AgentRole** — перечисление ролей агентов в пайплайне:
  - EXTRACTOR (извлечение терминов и отношений),
  - VERIFIER (верификация терминов и отношений),
  - CONFLICT_RESOLVER (разрешение конфликтов),
  - KG_INTEGRATOR (добавление в граф знаний, идентификация).

- **SharedState** — общее состояние между агентами: текст, упоминания терминов, термины, отношения; при необходимости — счётчики обнаруженных и разрешённых конфликтов. Есть преобразование в/из `AnalysisResult` для совместимости с существующим пайплайном.

### 1.2. Разрешение конфликтов между отношениями (`semantics_analysis/multi_agent/conflict_resolution.py`)

- **Понятие конфликта:** для одной пары сущностей (term1, term2) извлечено несколько разных предикатов — нужно оставить не более одного.

- **detect_relation_conflicts(relations)** — группирует отношения по паре (класс1, значение1, класс2, значение2) и возвращает только группы размера > 1 (конфликтные).

- **RelationConflictResolver** — агент, который для каждой конфликтной группы запрашивает у LLM выбор одного корректного отношения или ответ «ни одно не подходит». Используется промпт из `prompts/resolve_relation_conflict.txt`.

- **Расширения мультиагентности (два улучшения):**
  1. **Двухшаговый диалог** (`use_dialogue=True`): сначала LLM даёт краткое обоснование, какие варианты подходят к тексту; затем по этому обоснованию выбирает один вариант или «нет». Это делает решение более обоснованным и прозрачным.
  2. **Повторная верификация** (`reverify_callback`): после того как для конфликта выбран один предикат, можно дополнительно вызвать ту же верификацию, что и в извлекателе отношений (LLM отвечает «да/нет» по контексту). Если «нет» — выбранное отношение отбрасывается. Так мультиагентный шаг не только выбирает между вариантами, но и проверяет результат.

### 1.3. Оркестратор (`semantics_analysis/multi_agent/orchestrator.py`)

- **MultiAgentOrchestrator** запускает полный пайплайн: извлечение терминов → постобработка → верификация терминов → нормализация → разрешение референсов → извлечение отношений → **опционально** разрешение конфликтов (агент Conflict Resolver). Результат — `SharedState` (термины и отношения).

- Параметры:
  - `use_conflict_resolution` — включать ли шаг разрешения конфликтов;
  - `use_conflict_dialogue` — использовать двухшаговый диалог при разрешении;
  - `use_reverify_after_resolve` — после разрешения конфликта вызывать верификацию выбранного отношения (если у экстрактора отношений есть метод `verify_relation`).

- Метод **run_and_build_kg()** после пайплайна строит граф знаний (objects + relations) через `build_knowledge_graph` или переданный `kg_builder`.

### 1.4. Интеграция в пайплайн (`semantics_analysis/pipelines.py`)

- Добавлен шаг **ResolveRelationConflicts** — вызывает агент разрешения конфликтов по списку отношений в состоянии, подменяет список отношений на разрешённый. Используется только при мультиагентном режиме.

### 1.5. Конфигурация и точки входа

- **config.yml:** параметры `use-multi-agent`, `use-conflict-dialogue`, `use-reverify-after-resolve` (все описаны в `semantics_analysis/config.py`).
- **run_analysis.py** и **analyze_article.py:** при `use-multi-agent: true` собирают пайплайн с оркестратором, передают в него флаги диалога и реверификации, после выполнения строят граф знаний и сохраняют результат (в т.ч. `ont_entities.json`).

Итого: мультиагентность реализована как **последовательный пайплайн с явным агентом разрешения конфликтов** и двумя опциональными усилениями (диалог и повторная верификация). Это даёт возможность сравнивать в экспериментах базовый пайплайн и мультиагентный и описывать в ВКР.

## 2. Построение графа знаний

### 2.1. Модуль `semantics_analysis/knowledge_graph/kg_builder.py`

- **deduplicate_relations(relations)** — удаляет дубликаты по ключу (класс1, значение1, класс2, значение2, предикат).

- **build_knowledge_graph(terms, relations, deduplicate=True)** — перед конвертацией при необходимости дедуплицирует отношения, затем вызывает `ontology_entities.convert_to_ont_entities` и возвращает словарь с ключами `objects` и `relations` (готовый для сохранения в JSON и визуализации).

Граф строится после пайплайна (в т.ч. после разрешения конфликтов), чтобы в граф попадали уже «очищенные» отношения.

## 3. Оценка качества и сравнение

### 3.1. Датасет Кристины

- **scripts/convert_dataset_kristina_to_sentences.py** — конвертация датасета (CONLL с `# text =`, `# relations =`) в JSON предложений проекта; маппинг классов и предикатов (например, IsAlternativeNameFor → isAlternativeNameFor). Выход: `tests/dataset_kristina_sentences.json`.

- **scripts/evaluate_on_dataset_kristina.py** — оценка извлечения отношений на этом датасете:
  - по каждому типу отношений: precision, recall, F1, support;
  - micro (по всем парам) и macro (среднее по типам) — precision, recall, F1;
  - опции: `--multi-agent` (включить разрешение конфликтов перед подсчётом), `--limit N`, `--save-triples` (сохранить предсказанные тройки для метрик графа).
  - Результаты: `results/dataset_kristina_scores.json`, `results/dataset_kristina_metrics.md`, при `--save-triples` — `results/dataset_kristina_predicted_triples.json`.

### 3.2. Метрики на уровне графа (`calculate_graph_metrics.py`)

- Тройки задаются как (value1, predicate, value2).
- Эталонные тройки из предложений или из файла; предсказанные — из результатов извлечения, из ont_entities.json или из списка троек.
- **compute_graph_metrics(gold_triples, predicted_triples)** — считает TP, FP, FN, precision, recall, F1 на уровне троек.
- **structural_stats(triples)** — число узлов и рёбер.
- CLI: `python calculate_graph_metrics.py <gold_sentences.json> <predicted_file.json>` — записывает `results/graph_metrics.json` и `graph_metrics.md`.

### 3.3. Сравнение базового и мультиагентного пайплайна (`scripts/compare_pipeline_multiagent.py`)

- Запускает оценку **дважды** на одном датасете: без разрешения конфликтов (базовый) и с агентом разрешения конфликтов (мультиагентный). При этом собираются предсказанные тройки для обоих вариантов.
- Строит единое сравнение:
  - **Micro:** Precision, Recall, F1 и разница (мультиагентный − базовый).
  - **Macro:** Precision, Recall, **F1** (F1 считается как 2·P·R/(P+R) по macro P и R) и разница.
  - **По типам отношений:** таблица Baseline P/R/F1, Multiagent P/R/F1, Δ F1.
  - **Предсказанные тройки (граф):** для эталонных троек (из тех же предложений) считаются P/R/F1 по предсказанным тройкам базового и мультиагентного вариантов; выводится таблица с метриками и разницей, плюс количество троек (базовый, мультиагентный, эталон).
- Результаты: `results/compare_baseline_vs_multiagent.json` и `results/compare_baseline_vs_multiagent.md`.

Таким образом, для отчёта руководителю есть полный набор метрик: на уровне отношений (micro/macro и по типам) и на уровне графа (тройки), с явным сравнением «без агента» и «с агентом разрешения конфликтов».

## 4. Работа с LLM и окружением

- **semantics_analysis/llm_agent.py:** ключ API берётся из переменной окружения `OPENAI_API_KEY` (в т.ч. из `.env`); для совместимости с актуальным API используется `max_completion_tokens` вместо `max_tokens`; параметр `temperature` убран там, где модель не поддерживает его. Это устраняет типичные ошибки 400 при вызовах.
- Увеличены лимиты токенов в промптах (извлечение отношений, верификация, разрешение конфликтов, референция, нормализация и др.), чтобы снизить обрывы ответа по лимиту.
- В конфиге и коде по умолчанию используется модель `gpt-4o-mini` (при необходимости можно сменить в `config.yml`).

## 6. Краткое резюме для формулировки «что сделано»

- Введена **мультиагентная прослойка**: общее состояние (SharedState), роли агентов, оркестратор, шаг разрешения конфликтов в пайплайне.
- Реализован **агент разрешения конфликтов** между отношениями (одна пара сущностей — один предикат по выбору LLM) с опциями **двухшагового диалога** и **повторной верификации** выбранного отношения.
- Реализовано **построение графа знаний** с дедупликацией отношений и интеграцией в сценарии run_analysis / analyze_article при включённом мультиагентном режиме.
- Добавлена **оценка на датасете Кристины** (метрики по типам отношений, micro/macro) с опцией мультиагентного режима и сохранением троек.
- Добавлены **метрики на уровне графа** (P/R/F1 по тройкам) и **скрипт сравнения** базового и мультиагентного пайплайна с выводом micro, macro (включая macro F1) и метрик по графу в отчёт.
- Приведена в порядок работа с **LLM API** (ключ, лимиты токенов, параметры) и **документация** по проверке и идеям улучшений.

Этого достаточно, чтобы чётко описать руководителю объём работ и показать воспроизводимые эксперименты (сравнение базовый vs мультиагентный с метриками по отношениям и по графу).
