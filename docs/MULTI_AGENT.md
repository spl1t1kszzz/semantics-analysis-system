# Мультиагентная архитектура извлечения отношений

## Мотивация

Базовый пайплайн извлекает для каждой пары терминов **одно** отношение и принимает его как окончательное. Это приводит к ошибкам: LLM может ошибиться в выборе предиката, а механизма коррекции нет.

Мультиагентный подход разделяет задачу между несколькими специализированными LLM-агентами, каждый из которых отвечает за свой аспект. Это позволяет:
- генерировать **несколько кандидатов** отношений для одной пары терминов;
- **обнаруживать конфликты** (разные предикаты для одной пары);
- **разрешать конфликты** через отдельный LLM-агент с контекстом всех вариантов.

## Архитектура

```
                    Текст + Термины
                          |
                          v
              +-----------------------+
              |   Агент-экстрактор    |   (LLMRelationExtractor)
              |                       |
              |  detect_predicates()  |   -- возвращает ВСЕ подходящие
              |  для каждой пары      |      предикаты, а не один
              +-----------------------+
                          |
                   Relation[] (с конфликтами)
                          |
                          v
              +-----------------------+
              |  Детектор конфликтов   |   (detect_relation_conflicts)
              |                       |
              |  Группирует по паре   |   -- находит пары с >1 предикатом
              |  (term1, term2)       |
              +-----------------------+
                          |
                  конфликтные группы
                          |
                          v
              +-----------------------+
              |   Агент-резольвер     |   (RelationConflictResolver)
              |                       |
              |  Для каждого конфликта |   -- LLM выбирает лучший
              |  спрашивает LLM       |      предикат из вариантов
              +-----------------------+
                          |
                          v
                 Relation[] (без конфликтов)
```

## Компоненты

### 1. Агент-экстрактор (`LLMRelationExtractor`)

**Файл:** `semantics_analysis/relation_extraction/llm_relation_extractor.py`

Для каждой пары терминов, допустимой по онтологии:
1. Формирует промпт с описанием возможных отношений и примерами
2. Отправляет в LLM (OpenAI API)
3. Парсит ответ и возвращает **все** найденные предикаты (`detect_predicates()`)

Ключевое отличие от базового: метод `detect_predicates()` возвращает `List[Tuple[str, bool]]` -- все предикаты, упомянутые в ответе LLM, вместо единственного первого совпадения (`detect_predicate()`).

Для пар терминов одного класса (например, Method--Method) дополнительно определяет направление отношения (какой термин субъект, какой объект).

### 2. Детектор конфликтов (`detect_relation_conflicts`)

**Файл:** `semantics_analysis/multi_agent/conflict_resolution.py`

Группирует извлечённые отношения по ключу `(class1, value1, class2, value2)`. Если для одной пары найдено больше одного предиката -- это конфликт.

```python
# Пример конфликта:
# ("Method", "BERT", "Task", "NER") -> ["solves", "isUsedForSolving"]
# Два разных предиката для одной пары -> конфликт
```

### 3. Агент-резольвер (`RelationConflictResolver`)

**Файл:** `semantics_analysis/multi_agent/conflict_resolution.py`

Для каждой конфликтной группы:

1. Формирует промпт со всеми вариантами отношений
2. Спрашивает LLM, какой вариант верный в данном контексте
3. Возвращает 0 или 1 отношение

**Режимы работы:**

| Режим | Описание | Параметр конфига |
|-------|----------|------------------|
| Прямой выбор | LLM сразу выбирает номер варианта | (по умолчанию) |
| Двухшаговый диалог | Сначала LLM обосновывает, потом выбирает | `use-conflict-dialogue: true` |
| С реверификацией | После выбора -- дополнительная проверка через `verify_relation` | `use-reverify-after-resolve: true` |

#### Двухшаговый диалог (Chain-of-Thought)

При `use-conflict-dialogue: true`:

**Шаг 1 -- обоснование:**
> "Кратко обоснуй, какие варианты подходят к тексту, а какие нет. Не выбирай пока -- только оцени."

**Шаг 2 -- выбор:**
> "{обоснование агента}\n\nИсходя из твоего обоснования, выбери ровно один вариант."

Это реализует паттерн Chain-of-Thought: сначала рассуждение, потом решение.

### 4. Оркестратор (`MultiAgentOrchestrator`)

**Файл:** `semantics_analysis/multi_agent/orchestrator.py`

Собирает полный пайплайн из шагов и опционально добавляет шаг разрешения конфликтов. Передаёт единый `SharedState` между агентами.

## Роли агентов

Определены в `semantics_analysis/multi_agent/base.py`:

| Роль | Назначение |
|------|-----------|
| `EXTRACTOR` | Извлечение терминов и кандидатов отношений |
| `VERIFIER` | Верификация терминов и отношений |
| `CONFLICT_RESOLVER` | Поиск и разрешение конфликтов |
| `KG_INTEGRATOR` | Интеграция в граф знаний |

## Конфигурация

```yaml
app-config:
  use-multi-agent: true              # Включить мультиагентный режим
  use-conflict-dialogue: true        # Двухшаговый диалог при разрешении
  use-reverify-after-resolve: true   # Реверификация после разрешения
```

## Результаты сравнения

На датасете из 100 предложений (модель gpt-5.2):

| Метрика | Базовый | Мультиагентный | Разница |
|---------|---------|----------------|---------|
| Micro F1 | 0.7337 | 0.7439 | +0.0102 |
| Macro F1 | 0.6800 | 0.6838 | +0.0038 |
| Граф F1 | 0.5285 | 0.5377 | +0.0092 |

Мультиагентный подход показывает улучшение по всем метрикам за счёт корректного разрешения конфликтов между отношениями.
