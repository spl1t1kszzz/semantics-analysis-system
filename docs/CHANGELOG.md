# Проделанная работа

Изменения относительно `master` в `aiwannafly/semantics-analysis-system`.

## 1. Мультиагентная система разрешения конфликтов

Разработана и интегрирована в пайплайн мультиагентная архитектура для повышения качества извлечения семантических отношений. Подробное описание: `docs/MULTI_AGENT.md`.

### Multi-probe извлечение отношений
- Реализован метод `detect_predicates_multi_probe()` — для каждой пары терминов один LLM-вызов с **бинарным «да/нет» по каждому возможному предикату** независимо
- Это принципиально отличается от базового подхода (`detect_predicate()`), где модель выбирает один предикат — multi-probe позволяет обнаружить несколько подходящих отношений за один вызов
- Новый промпт `prompts/relation_extraction_multi_probe.txt` — структурированный формат с примерами из онтологии и ожидаемым форматом ответа
- Включается автоматически при `use-multi-agent: true` (параметр `use_multi_probe` в `LLMRelationExtractor`)

### Улучшение промптов
- **`prompts/relation_extraction.txt`** — разрешено перечисление нескольких отношений вместо «только один ответ»
- **`prompts/verify_relation.txt`** — добавлен параметр `{relation_description}` с семантикой отношения из онтологии, усилена инструкция оценивать строго по тексту
- **`prompts/resolve_relation_conflict.txt`** — добавлен повтор имён терминов в инструкции выбора

### Адаптивная стратегия извлечения
- Multi-probe используется **только для пар классов с >1 возможным предикатом** — для пар с единственным предикатом конфликтов быть не может, а стандартный промпт с rich few-shot примерами точнее
- Это предотвращает ложные срабатывания на простых парах (например, `Metric_isUsedIn_Task`)

### Исправление парсинга ответов LLM
- `detect_predicates()` — убрана агрессивная фильтрация «нет»: раньше если «нет» встречалось **где угодно** в ответе, все предикаты отбрасывались (ломало ответы вида «нет, не X, но Y»); теперь проверяется только начало ответа и паттерн «Ответ: нет»

### Архитектура агентов (`semantics_analysis/multi_agent/`)
- **`base.py`** — определены роли агентов (`AgentRole`: EXTRACTOR, VERIFIER, CONFLICT_RESOLVER, KG_INTEGRATOR) и общее состояние `SharedState` для передачи данных между агентами
- **`conflict_resolution.py`** — реализован `RelationConflictResolver`:
  - Детекция конфликтов: поиск пар терминов с несколькими различными предикатами
  - Разрешение через LLM: выбор наиболее подходящего отношения из конфликтной группы
  - Опции конфликта содержат **описания предикатов** из онтологии (а не голые имена)
  - Контекст вырезается **вокруг терминов** (±500 символов с расширением до границ предложений), а не с начала текста
  - Два режима: прямой выбор и двухшаговый диалог (Chain-of-Thought: сначала обоснование, затем выбор)
  - Опциональная повторная верификация выбранного отношения
- **`orchestrator.py`** — `MultiAgentOrchestrator` координирует все этапы пайплайна и опционально запускает разрешение конфликтов

### Промпты для мультиагентного режима
- `prompts/relation_extraction_multi_probe.txt` — multi-probe извлечение (один вызов, бинарный ответ по каждому предикату)
- `prompts/resolve_relation_conflict.txt` — разрешение конфликтов с описаниями предикатов

### Модуль построения графа знаний (`semantics_analysis/knowledge_graph/`)
- **`kg_builder.py`** — дедупликация отношений и конвертация в онтологические объекты
- Построение финального графа знаний с учётом результатов разрешения конфликтов

### Шаг пайплайна
- Добавлен `ResolveRelationConflicts` как опциональный завершающий шаг в `pipelines.py`
- Включается/выключается через конфигурацию (`use-multi-agent: true/false`)

### Конфигурация мультиагентного режима
```yaml
use-multi-agent: true
use-conflict-dialogue: true        # двухшаговый диалог (Chain-of-Thought)
use-reverify-after-resolve: true   # повторная верификация
```

### Результаты сравнения

Актуальные результаты сохраняются при каждом запуске `scripts/compare_pipeline_multiagent.py` в `results/compare_baseline_vs_multiagent.json` и `.md`.

### Скрипты оценки
- **`scripts/evaluate_on_dataset_kristina.py`** — оценка качества извлечения отношений на размеченном датасете (precision, recall, F1 по типам отношений)
- **`scripts/compare_pipeline_multiagent.py`** — сравнение базового пайплайна и мультиагентного: два прохода по одному датасету, отчёт об улучшениях
- **`scripts/convert_dataset_kristina_to_sentences.py`** — конвертация датасета в формат для оценки

## 2. Архитектурный рефакторинг

### Реорганизация структуры проекта
- Модули `ontology_entities.py`, `parse_habr.py`, `plot_graph.py` перенесены из корня в пакет `semantics_analysis/`
- Утилитарные скрипты перенесены в `scripts/`
- На верхнем уровне остались только два entry point: `run_analysis.py` и `analyze_article.py`

### Фабрика пайплайна и Dependency Injection
- Создан `semantics_analysis/factory.py` с функциями `build_pipeline()` и `build_term_extractor()`
- Единый `LLMAgent` создаётся один раз и передаётся во все компоненты
- `run_analysis.py` упрощён с ~170 до ~60 строк

### Упрощение pipeline
- 6 классов-обёрток заменены на простые функции
- `SequencePipeline` принимает любые callable
- Conflict resolution интегрирован как обычный шаг пайплайна

### Рефакторинг конфигурации
- `Config` переписан как `@dataclass` с дефолтными значениями
- Хардкоды вынесены в конфиг: `term_threshold`, `class_threshold`, `max_term_distance`

## 3. Удаление мёртвого кода (~990 строк)
- Удалён `semantics_analysis/meaning_model/` (4 файла, не используется)
- Удалён `sentence_bert_llm_term_mention_extractor.py` (не импортируется)
- Удалён обфусцированный `values.py` — заменён нормальным retry с экспоненциальным backoff
- Удалён неиспользуемый параметр `use_all_tokens` из всех компонентов
- Удалена зависимость `termcharts`
- Удалён `spinner.py` (не используется)

## 4. Устранение дублирования
- Создан `semantics_analysis/constants.py` — единый источник для 16 онтологических классов
- Убрано дублирование `LABEL_LIST` между модулями

## 5. Поддержка нескольких LLM-провайдеров
- `LLMAgent` поддерживает **OpenAI** и **Anthropic (Claude)** API — выбор провайдера автоматический по имени модели
- Модели с префиксом `claude-` маршрутизируются через Anthropic SDK, остальные — через OpenAI SDK
- Совместимость с OpenAI-совместимыми провайдерами (Groq, OpenRouter и др.) через `OPENAI_API_BASE`
- `temperature=0` для детерминированных результатов (воспроизводимость экспериментов)
- Retry с экспоненциальной задержкой (до 5 попыток)

## 6. Поддержка прокси
- Переменная `OPENAI_PROXY` для маршрутизации запросов через HTTP/HTTPS/SOCKS5 прокси
- `.env.example` с примером настройки
